INTRODUCTION						*jin-introduction*

vim-jin runs jj, shows what jj prints in buffers, and lets you act on the
lines of those buffers. It is meant for watching and following a repository
while you, or an agent, work on it.

	:Jin new
	:Jin ++wait describe -m "feat: add parser"
	:JinLog -r 'trunk()..@'

Every vim-jin buffer is read-only and tied to no file; its name starts with
"jin://" and records everything needed to read it again.

=============================================================================
REQUIREMENTS						*jin-requirements*

- jj 0.46 on $PATH. vim-jin follows one jj release at a time, and another
  may print what it reads differently.
- Neovim 0.10 or later, or Vim 9.0.0067 or later built with |+lua|.

=============================================================================
COMMANDS						*jin-commands*

Arguments are split the way a POSIX shell splits them, so a command copied
from a terminal means the same here: white space separates them, single
quotes take everything literally, double quotes everything but an escaped
`"` or `\`, and outside quotes a backslash escapes the next character. `|`
does not end the command, so a revset such as `root()|@` reaches jj intact.
No variable, glob or `~` is expanded.

							*jin-%*
A bare `%` stands for the file of the current buffer, relative to its
workspace root; in a |:JinFile| buffer, for the file it shows.

Every command runs jj in the workspace of the current buffer, falling back
to the workspace of the current directory, or, outside any workspace, in the
current directory itself. All of them complete their arguments with what
the installed jj offers.

							*:Jin*
:Jin [++option...] [{args}]
	Run `jj {args}` and echo what it printed, in |hl-ErrorMsg| when it
	fails. jj runs in the background, and |User_JinCommandPost| fires
	once it has finished.

	++wait		Return only after jj has finished.

							*:JinBuffer*
:JinBuffer[!] [++option...] [{args}]
	Open a buffer showing what `jj {args}` prints, in jj's own colors.
	The buffer opens at once and fills when jj answers. Opening one
	already open switches to it; with [!] it reads jj again first.
	`:edit` reads jj again too.

	++opener={opener}	Open the buffer with {opener} (`split`,
				`vsplit`, `tabedit`, ...) instead of
				|:edit|. Modifiers such as |:botright|
				apply as well.
	++monochrome		Ask jj for output without colors.
	++filetype={filetype}	Set the filetype of the buffer.

:JinLog [args]						*:JinLog*
	`jj log`, in your log template. jj's own word wrapping is turned
	off so that the text and the changes stay aligned; set 'wrap' to
	wrap.

:JinShow [args]						*:JinShow*
	`jj show`, with the diff in color-words format.

:JinDiff [args]						*:JinDiff*
	`jj diff` in color-words format, each file folded (opened).

:JinFile [args]						*:JinFile*
	`jj file show`, highlighted with the filetype of the file. It needs
	the path of a file, such as `%`.

:JinOpLog [args]					*:JinOpLog*
	`jj op log`: every operation on the repository, an agent's included.

:JinEvolog [args]					*:JinEvolog*
	`jj evolog`: the versions a change went through, newest first.

:JinStatus [args]					*:JinStatus*
	`jj status`: the changes of the working copy and the paths left in
	conflict.

:JinAnnotate [args]					*:JinAnnotate*
	`jj file annotate`: the file itself, highlighted with its filetype,
	with which change wrote each line shown before the line. Searching
	and yanking see the file alone. It needs the path of a file, such
	as `%`.

	A line too long for the window wraps after the annotation: while
	the window shows the view, 'breakindent' is on there and the
	"shift" of 'breakindentopt' is as wide as the annotation, the other
	items you set kept. Once the window shows another buffer, it has
	that buffer's values again. 'showbreak' shows after the shift, or
	before it with "sbr". A "min" you set still holds, so in a window
	too narrow for it a wrapped line goes on below the annotation;
	without one it is set to 1, so that a wrapped line goes on beside
	the annotation however narrow the window.

:JinBookmark [args]					*:JinBookmark*
	`jj bookmark list`.

:JinWorkspace [args]					*:JinWorkspace*
	`jj workspace list`.

:JinConflicts [args]					*:JinConflicts*
	The log of the changes that hold conflicts.

The view commands take the `++` options and [!] of |:JinBuffer|.

:JinCd							*:JinCd*
:JinLcd							*:JinLcd*
:JinTcd							*:JinTcd*
	Change the current directory, globally, for the window, or for the
	tab page, to the root of the current buffer's workspace.

VIEWS							*jin-views*

The buffers of the view commands are views: their lines know what they
stand for, so actions on a line lead somewhere. A view follows the
repository: it reads jj again after every |:Jin| or |jin.command()|, and,
when jj changed the repository outside the editor, in another terminal or
by an agent, on entering it or when the editor regains focus. A view at a
given operation (`--at-op`) stays as it is; one relative to the latest,
such as `--at-op @-`, moves on with it. Reading a view snapshots the
working copy, as jj does, so files changed without jj show, unless every
view of the workspace is given `--ignore-working-copy` or `--at-op`.

In the log, the evolog, the operation log and the conflicts, all the
lines of the change, version or operation under the cursor are
highlighted with |hl-JinCursorEntry|; in the status, the bookmarks, the
workspaces and the conflicted paths, one thing to a line, the line under
the cursor is. In the annotation, every line the change of
the line under the cursor wrote is highlighted with |hl-JinCursorChange|.

A buffer that was left and read again on coming back to it, as with
|CTRL-O|, puts the cursor back where it was.

ACTIONS							*jin-actions*

Each action of a view is mapped as `<Plug>(jin-action-{name})` in normal
mode, on the cursor line, and in visual mode, on the selected lines. Every
view has these:

	choice		Ask for an action by name, with completion.
	repeat		Run the action last chosen with choice again.
	help		List the actions with the keys mapped to them.

An action that opens a view comes with `{name}:split`, `{name}:vsplit` and
`{name}:tab`, which open it in a new window. A view opened from a change
names it by its change ID, so that it follows the change through rewrites,
or by its commit ID when the change is divergent or the commit is hidden, as
an older version of a change is.

A key pressed on a line that names nothing to act on does nothing; the same
action chosen by name says why it cannot run.

Log and conflicts ~
	show		Show the change of the line.
	diff		Show its diff.
	evolog		Show the versions it went through.
	yank:change	Yank the change IDs of the lines.
	yank:commit	Yank their commit IDs.
	files		(conflicts) List the conflicted paths of the change.

Conflicted paths ~
	edit		Open the file with its conflict, the cursor on the
			first one: the file itself in the working copy, or
			|:JinFile| of the change.
	diff		Show the diff of the path in the change.

Show, diff and interdiff ~
	jump		Open the file of the line at that line: the working
			copy file itself, or |:JinFile| of another revision.
	jump:old	Open it on the old side.
	jump:new	Open it on the new side.
	parent		(show) Show the parent of the change.
	child		(show) Show its child.
	yank:change	(show) Yank the change ID.
	yank:commit	(show) Yank the commit ID.

File ~
	annotate	Annotate the file, on the same line.
	log		Show the log of the changes that touched the file.

Annotate ~
	show		Show the change that wrote the line.
	diff		Show its diff.
	log		Show the log up to that change.
	file		Show the file without the annotation.
	log:file	Show the log of the changes that touched the file.
	yank:change	Yank the change IDs of the lines.
	yank:commit	Yank their commit IDs.

Operation log ~
	show		Show what the operation changed, the changes it
			touched leading on to show and diff.
	log		Show the log as it was right after the operation.
	yank:operation	Yank the operation IDs of the lines.

Operation show ~
	show, diff	Show the version on the line, or its diff, by its
			commit ID, even one the operation rewrote away.
	yank:change	Yank the change IDs of the lines.
	yank:commit	Yank their commit IDs.

Evolog ~
	interdiff	Show how the version's diff differs from that of the
			version before it.
	show		Show the version.
	yank:change	Yank the change IDs of the lines.
	yank:commit	Yank their commit IDs.

Status ~
	inspect		Show the diff of the path of the line, or the change
			of the working copy or of a parent on their lines.
	open		Open the file of the line, or show the change of the
			working copy or of a parent on their lines.
	edit		Open the file of the line.
	diff		Show the diff of the path.
	annotate	Annotate the file of the path.
	yank:path	Yank the paths of the lines.

A conflicted file opens with the cursor on its first conflict.

Bookmark ~
	log		Show the log up to the bookmark.
	show		Show the change it points to.
	yank:bookmark	Yank the bookmark names.

Workspace ~
	tcd		Change the tab page's directory to the workspace root.
	cd, lcd		Likewise, globally or for the window.
	log		Show the log up to the workspace's working copy.
	show		Show that change.

KEY MAPPINGS						*jin-mappings*

Each view maps a few keys, by these rules, and none of them changes what
the key means in Vim. A key either keeps its meaning while the view tells
what it applies to, as |yy| still yanks, |]]| still goes
to the next section and <CR> goes to what the line names as it does in the |quickfix-window|, or it is a
key that edits text, which a read-only buffer has no use for, given the
change closest to what it does to text. Vim's motions and marks keep
working, and |=| stays Vim's operator. `a`, `.` and `?` are the deliberate
exceptions. A view maps only the keys of the actions it has.

	a		choice
	.		repeat
	?		help
	<CR>		What the view is opened for: show in the log, jump in
			a diff, annotate in a file view, interdiff in the
			evolog, inspect in the status, and so on.
	<S-CR> <C-CR>	What it is opened for next most often, such as diff
			in the log or log in a file view. Both are mapped,
			as a terminal may pass on only one of them.
	<C-w><CR>	What <CR> opens, in a new window, split vertically
			when 'diffopt' holds "vertical".
	gf		The file: |:JinFile|, or the file itself in the
			status and the conflicted paths.
	gd		The diff; the interdiff in the evolog.
	gp gc		The parent, the child.
	yy		Yank what the line stands for; `y` in visual mode.
	YY		Yank commit IDs; `Y` in visual mode.
	]] [[		Go to the first line of the next, or the previous,
			block; see |jin-blocks|.

Keys that start others, as `g` and CTRL-W do, wait 'timeoutlen' for
the rest. The openers without a key and the variants have no key: reach
them with `a`, or map their <Plug>.

`?` shows the keys of the view at hand.

					*jin-blocks*
					*<Plug>(jin-next-block)*
					*<Plug>(jin-prev-block)*
In a view that has blocks, `]]` and `[[` go between them as Vim's own
section motions go between sections (|]]|): with a count, in visual and
operator-pending mode too (`V]]`, `y]]`), leaving where they came from in
the |jumplist|. A count past the last block stops at it; with no block that
way, the cursor stays. A block is:

- in |:JinAnnotate|, a run of lines one change wrote;
- in |:JinLog|, |:JinConflicts|, |:JinEvolog| and |:JinOpLog|,
  an entry, all its lines;
- in |:JinDiff| and the interdiff, a file;
- in |:JinShow|, the header of each change, and each file.

The other views have no blocks and leave `]]` and `[[` to Vim. The keys
are mapped to `<Plug>(jin-next-block)` and `<Plug>(jin-prev-block)`, which
are there even when |g:jin_{view}_disable_default_mappings| is set:
>vim
	autocmd FileType jin-log nmap <buffer> <C-n> <Plug>(jin-next-block)
<

A key the buffer already maps itself, as your own |ftplugin| may for the
filetype of a view, is left as it is. Map any `<Plug>(jin-action-{name})`
to keys of your own:
>vim
	autocmd FileType jin-log nmap <buffer> <Leader>e <Plug>(jin-action-evolog)
<
				*g:jin_{view}_disable_default_mappings*
To map no key at all in a view, set this to 1, `{view}` being `log`,
`show`, `diff`, `interdiff`, `file`, `oplog`, `opshow`, `evolog`,
`status`, `annotate`, `bookmark`, `workspace`, `conflicts`,
`resolve` (the conflicted paths `files` lists) or `buffer` (|:JinBuffer|):
>vim
	let g:jin_log_disable_default_mappings = 1
<

HIGHLIGHT AND VARIABLES					*jin-highlight*

							*hl-JinCursorEntry*
JinCursorEntry		The lines of the change, version or operation under
			the cursor, or the line under it in a view of one
			thing a line. Links to |hl-CursorLine| by default.

							*hl-JinCursorChange*
JinCursorChange		In |:JinAnnotate|, every line written by the change
			of the line under the cursor. Links to |hl-CursorLine|
			by default.

							*b:jin_title*
b:jin_title		A short title of a vim-jin buffer, such as
			"jj log -r @-", for a statusline or a tabline in place
			of its long name:
>vim
	set statusline=%{get(b:,'jin_title',expand('%'))}
<

COMPONENTS						*jin-components*

						*jin#component#get()*
jin#component#get({name})
	A short string about the workspace of the current buffer, for
	'statusline', 'tabline' or 'winbar':

	change		The shortest unique prefix of the working-copy
			change ID.
	description	The first line of its description.
	state		"empty", "conflict" and "divergent", as they apply.
	bookmarks	The nearest bookmarks at or below the working copy.
	traffic		Those tracked on a remote and not in step with it, as
			"name@remote" with "↑n" ahead and "↓n" behind.
	workspace	The workspaces whose working copy is this change, when
			there are several.

	It never runs jj and never fails: it returns what the last refresh
	found, or "" before it, outside any workspace, or for an unknown
	name. Refreshes run in the background without snapshotting the
	working copy or adding an operation, so watching never changes what
	an agent sees.
>vim
	set statusline+=%{jin#component#get('change')}
	autocmd User JinComponentPost redrawstatus
<

LUA API							*jin-lua*

`require("jin")` works in Neovim and in Vim built with |+lua|. Each function
runs jj in the workspace of `opts.cwd` when given, or else as |:Jin| would.

						*jin.jj()*
jin.jj({argv} [, {opts} [, {on_exit}]])
	Run jj and return `{ code, stdout, stderr }`, echoing nothing and
	firing no event. With {on_exit}, return at once and call it with
	the result. `opts.color` asks for ANSI colors, `opts.env` adds
	environment variables.

						*jin.command()*
jin.command({argv} [, {opts} [, {on_exit}]])
	Do what |:Jin| does. `opts.wait` stands for `++wait`.

						*jin.buffer()*
jin.buffer({argv} [, {opts}])
	Do what |:JinBuffer| does and return the buffer number. `opts` takes
	`opener`, `monochrome`, `filetype`, `mods` and `reload` (the [!]).

						*jin.view()*
jin.view({name}, {argv} [, {opts}])
	Do what the view command of {name} does, `"log"` for |:JinLog| and
	so on, and return the buffer number. `opts` is as for
	|jin.buffer()|, plus `line`, the line to put the cursor on.

						*jin.component()*
jin.component({name})
	The same as |jin#component#get()|.

						*jin.root()*
jin.root([{path}])
	The root of the workspace holding {path}, or of the current buffer
	or directory; nil outside any workspace.
